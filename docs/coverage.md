# What the properties cover

This catalog lists arrow-rs's public entry points by crate, what covers each, and what was measured. Entry points marked "Not covered" have no property yet. "Covered" means a property calls the entry point and checks its output against the oracle, a law, a round trip, or the format. "Indirect" means a covered kernel calls it internally, so a bug there can surface but the property does not aim at it. The catalog lists the entry points of arrow-rs `main` at 30c5c3287c, whose last release is 60.1.0. Issue numbers without a repository are in apache/arrow-rs. The Issues columns list every bug found in an entry point, open or fixed, and [known-bugs.md](known-bugs.md) says which are fixed.

Mutation testing has been run on `arrow-select` only, at arrow-rs `main` 70d8190350 on 2026-10-28 (see [tools/mutation/README.md](../tools/mutation/README.md)). The rates below are mutants killed by the properties and by the crate's own tests, out of the viable mutants in each file.

## Parquet

Parquet is the largest crate in arrow-rs and has no properties here yet. proptest entered arrow-rs in [apache/arrow-rs#10352](https://github.com/apache/arrow-rs/issues/10352), which checks that `parquet-variant` decoding never panics on malformed bytes and that the variant builder's output reads back unchanged. [apache/arrow-rs#11485](https://github.com/apache/arrow-rs/issues/11485) then added differential tests that vary the scan (projection, row selection, row filters, page index policy, batch size) over a few fixed files and check that `ParquetPushDecoder` returns the same rows as `ParquetRecordBatchReader`. Those files hold a handful of `Int64`, list, struct and string columns written with fixed writer settings. The generator adds the dimension they keep fixed: the data. These properties would cover it:

1. **Round trip.** `ArrowWriter` then `ParquetRecordBatchReader` returns the oracle's values and the original type, for every type Parquet can store, in every layout the generator makes. Writer properties vary per case: dictionary encoding, data page size and row limits, row group size, write batch size, writer version, compression codec, encodings, and statistics level. A type the writer documents as unsupported is an asserted error, not a discard.
2. **Corrupted files.** A round-trip file with one byte changed, or truncated, makes each reader return an error or valid output, never a panic.
3. **Schema.** The written Parquet schema follows the spec's rules for logical type annotations, decimal storage, and the list and map structures.
4. **Statistics.** Column chunk statistics (minimum, maximum, null count) match the oracle's values under Parquet's ordering for each logical type: signed and unsigned integers, floats with NaN and negative zero, decimals, and byte arrays. `FLOAT16` has its own rules, so this waits for Float16 in the generator.
5. **Bloom filters.** Every non-null value written is found in its column's bloom filter.
6. **Page index.** The offset index and the file metadata are consistent, and each page's column index bounds and counts hold that page's values.
7. **Readers agree.** The sync reader, the async reader and the push decoder return the same rows for the same file and scan, extending [apache/arrow-rs#11485](https://github.com/apache/arrow-rs/issues/11485) from fixed files to generated ones.
8. **Scans select the right rows.** A projection, a row selection, or a row filter returns what selecting from the oracle's values returns, with and without the page index, and for every batch size.
9. **Nested levels.** A model of definition and repetition levels, computed from the oracle's values, checks the level counts, the level histograms, and the null count of nested columns.

## Other formats

`arrow-json`, `arrow-csv` and `arrow-avro` have no properties. Writing an array and reading it back needs no new oracle: the generator and the oracle's equality already exist. Each format supports a subset of the types, so each needs a case strategy restricted to its documented types, and to its documented lossy conversions.

## Downstream projects

Each downstream project is tested through an adapter crate in this repository, as [Downstream adapters](design.md#downstream-adapters) in the design describes.

`arrow-pbt-datafusion` checks two laws for 58 of DataFusion's scalar functions, with no model. The broadcast law says that calling a function with some arguments as scalars gives the same result as calling it with those scalars broadcast to arrays. The row-by-row law says that each row of a call equals the call with every argument as that row's scalar. Arguments come from `ValueDomain::Logical`, so every decimal fits its declared precision, as DataFusion requires. It does not cover DataFusion, which would be a project of its own.
